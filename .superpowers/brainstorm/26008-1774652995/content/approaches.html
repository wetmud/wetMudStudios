Architecture Approaches

Three ways to structure the lead gen pipeline. Pick the one that fits.

A

Monorepo — One Folder, Everything Together

Single leadgen/ folder: Python scraper + Node.js API server + vanilla HTML/JS CRM frontend. SQLite database lives locally. Run with one command. Deploy scraper + API to Railway, CRM as static files to GitHub Pages.

Pros

  • Simple to reason about
  • One repo, one deploy
  • Easy to hand off

Cons

  • CRM is public unless you add auth
  • Tighter coupling if it grows
B

Split — Scraper CLI + Separate CRM App

Scraper is a standalone Python CLI you run locally — outputs to SQLite. CRM is a separate Node.js/Express app that reads the same DB and serves a UI. Two processes, clean separation.

Pros

  • Scraper stays local (no hosting cost)
  • CRM can evolve independently
  • Easier to open-source the scraper separately

Cons

  • Two things to run/maintain
  • DB sync gets tricky if you ever go multi-user
C

Unified Node.js App — API + Scraper + CRM

Single Node.js server handles everything: scrape jobs (using Playwright), REST API, and serves the CRM frontend. SQLite via better-sqlite3. One process, one deploy to Railway.

Pros

  • One language throughout
  • Single deploy, single process
  • Easiest path to adding auth + multi-user later

Cons

  • Node + Playwright is heavier than Python scraping
  • Slightly more complex to set up locally

⭐ Recommended: C — unified Node.js keeps everything in one place, one deploy, and sets you up best for eventually productizing it with auth + multi-tenancy.
